# Monorepo skeleton

## Why

The store's four prompts are per-app build templates: they describe a .NET API and a TanStack SSR
frontend in detail, and say nothing about the workspace that holds them. Everything a real repo
needs above the app line — Nx task wiring, commit hygiene, a local dev stack, coverage tooling,
release automation, the public proxy — has been built and refined in a live repo and exists nowhere
in the store. A fresh project following these prompts gets two apps and no workspace.

The prompt set also duplicates itself. `cookie-auth-ssr` shares 121 of its 295 lines with
`fe-ssr-tanstack`, and `cookie-auth-direct` shares 125 of 363 with `dotnet-webapi` — each auth
prompt is largely its app prompt plus auth, and the two auth prompts share only 12% with each other.
Four entries carry three prompts' worth of content, and the copies drift.

## What Changes

- **New prompt `nx-monorepo`** (`appPattern: nx-monorepo`): the workspace skeleton, generalised from
  a production repo. Nx task wiring and release groups, pnpm workspace with a pinned package
  manager, husky + commitlint + lint-staged, root formatting and spelling config, a
  docker-compose local dev stack, test/coverage scripts, an nginx proxy app as the single public
  entrypoint, and deploy wiring.
- **`dotnet-webapi` absorbs the BE half of `cookie-auth-ssr`** — cookie session, token resolution,
  and the private-behind-a-BFF posture become part of the API template rather than a separate entry.
- **`fe-ssr-tanstack` absorbs the FE half of `cookie-auth-ssr`** — the auth proxy route, cookie
  re-homing, and the Keycloak harness become part of the frontend template.
- **BREAKING: `cookie-auth-direct` and `cookie-auth-ssr` are removed.** The `bff-cookie-auth`
  appPattern disappears with them. Installs referencing either id will fail. The Direct BFF
  architecture (browser calling the API directly) is dropped rather than merged: it shares almost
  nothing with the SSR architecture, and SSR is the shape in production use.
- **New skill `monorepo-hygiene`**: audits an existing repo against the same workspace shape,
  reports what is missing, and applies what the user approves. Retrofit, where the prompt is
  greenfield.
- **Third-party and org-specific values genericised on the way in** — an internal container
  registry and a vendor-specific integration are placeholders or dropped, matching the store's
  existing zero-leakage property.

## Capabilities

### New Capabilities

- `monorepo-hygiene`: the behavioural contract of the retrofit skill — what it inspects, what it
  reports, what it may change, and the consent it needs before changing anything.

### Modified Capabilities

None. No existing spec constrains which prompts the store ships or what a prompt's body says;
the prompt restructure is content. `prompt-install` and `skill-catalog` are unaffected — the new
prompt uses the existing item shape, and removing entries needs no requirement change.

## Impact

- **New:** `prompts/nx-monorepo/PROMPT.md` plus its supporting files; `skills/monorepo-hygiene/`.
- **Modified:** `prompts/dotnet-webapi/PROMPT.md`, `prompts/fe-ssr-tanstack/PROMPT.md`,
  `catalog.json` (26 → 26: two prompts removed, one prompt and one skill added).
- **Removed:** `prompts/cookie-auth-direct/`, `prompts/cookie-auth-ssr/`.
- **Release:** the breaking removal is recorded through a conventional-commit `!` / `BREAKING
  CHANGE:` footer. `CHANGELOG.md` is generated by `nx release`, so it is not hand-edited.
- **Consumers:** anyone running `ai-skills add cookie-auth-ssr` or `cookie-auth-direct` breaks on
  the next release; the merged prompts cover the SSR path, and the Direct path is gone.
- **Not in scope:** shipping a CI pipeline file — CI is the most environment-shaped part of the
  source repo, and a generic one teaches little. The prompt documents the Nx targets a pipeline
  should call and stops there.
